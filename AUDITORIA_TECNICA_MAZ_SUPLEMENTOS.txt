1. RESULTADO EJECUTIVO
============================================================

Maz-Suplementos es una aplicación web funcional para administrar un
catálogo de suplementos, inventario, pedidos, usuarios y respaldos. Está
construida con un frontend web sin frameworks, un backend en Go y TiDB
Cloud Data Service como capa de acceso a la base de datos.

Resultado general: APROBADA CON OBSERVACIONES.

La aplicación:

- Compila correctamente.
- Supera todas las pruebas automatizadas existentes.
- Pasa go vet, formato Go y validación sintáctica de JavaScript.
- Se comunica correctamente con TiDB Data Service.
- Implementa autenticación, sesiones, CSRF y control de acceso por roles.
- Mantiene las credenciales de TiDB únicamente en el servidor.
- Genera respaldos descargables en formato .sql.
- Conserva la sesión al hacer clic en el título y volver al inicio.
- Está sincronizada con el repositorio remoto.
- No contiene credenciales conocidas dentro de los archivos rastreados
  ni en el historial Git revisado.

Es adecuada para entrega académica, demostración y uso interno controlado.
Antes de considerarla preparada para producción pública deben atenderse
aspectos como despliegue HTTPS, rotación de secretos, respaldos
transaccionales, auditoría persistente, integración continua y limitación
distribuida de solicitudes.

No se encontraron defectos críticos o altos durante esta revisión.


2. DESCRIPCIÓN DEL SISTEMA
============================================================

Maz-Suplementos permite:

- Consultar suplementos públicos.
- Buscar productos por nombre o marca.
- Filtrar por precio, existencia, categoría, objetivo e ingrediente.
- Consultar los detalles de un suplemento.
- Mantener un carrito local.
- Registrar pedidos.
- Administrar suplementos e inventario.
- Administrar categorías, objetivos e ingredientes.
- Consultar y actualizar el estado de los pedidos.
- Crear y administrar usuarios con distintos roles.
- Desactivar usuarios sin eliminarlos físicamente.
- Descargar un respaldo SQL desde el navegador.
- Mantener sesiones protegidas con cookies y CSRF.

No incluye actualmente:

- Pasarela de pagos.
- Facturación fiscal.
- Integración con ERP, CRM o paqueterías.
- Recuperación automática de contraseña por correo.
- Bitácora histórica completa de modificaciones.
- Despliegue productivo administrado.
- Restauración automática de respaldos desde la interfaz.


3. ARQUITECTURA
============================================================

Navegador
   |
   | HTTP/HTTPS, JSON y cookies
   v
Servidor Go / BFF
   |
   | HTTPS y Basic Authentication
   v
TiDB Cloud Data Service
   |
   | SQL parametrizado

El navegador nunca se conecta directamente a TiDB ni conoce sus
credenciales.

- Autenticar al usuario.
- Administrar sesiones.
- Validar CSRF.
- Verificar roles.
- Validar entradas.
- Limitar solicitudes sensibles.
- Llamar a endpoints predefinidos de TiDB Data Service.
- Normalizar errores.
- Servir el frontend.
- Construir y entregar respaldos SQL.

Tecnologías principales:

- Frontend: HTML5, CSS y JavaScript ES Modules.
- Backend: Go 1.24.
- Base de datos: TiDB Cloud.
- Acceso a datos: TiDB Cloud Data Service.
- Contraseñas: bcrypt.
- Sesiones: tokens criptográficos y cookies.
- Pruebas de backend: go test.
- Pruebas de navegador: Playwright.
- Control de versiones: Git y GitHub.

Dependencia externa principal del backend:

golang.org/x/crypto v0.36.0

6. MODELO DE DATOS
============================================================

La base contiene 11 tablas.

6.1 users
------------------------------------------------------------

Almacena:

- Identificador.
- Nombre de usuario único.
- Hash bcrypt de contraseña.
- Nombre completo.
- Rol.
- Estado activo/inactivo.
- Fechas de creación y modificación.

Roles admitidos:

- ADMINISTRADOR
- CAPTURISTA
- AUDITOR

Las contraseñas no se almacenan en texto plano.

6.2 Catálogos
------------------------------------------------------------

Tablas:

- categories
- goals
- ingredients

Cada catálogo maneja ID, nombre único, descripción, estado activo y
fechas de creación y actualización.

6.3 supplements
------------------------------------------------------------

Almacena nombre, marca, descripción, precio, existencias, presentación,
sabor, peso, URL de imagen, estado activo y fechas. Incluye restricciones
para evitar precios o inventarios inválidos.

6.4 Relaciones muchos-a-muchos
------------------------------------------------------------

- supplement_categories
- supplement_goals
- supplement_ingredients

Estas tablas conectan suplementos con categorías, objetivos e
ingredientes. Las relaciones se eliminan en cascada cuando desaparece el
suplemento. Los catálogos están protegidos para impedir eliminaciones que
dejen referencias inconsistentes.

6.5 orders
------------------------------------------------------------

Almacena ID generado desde una clave idempotente, número de pedido MAZ,
datos del cliente, estado, subtotal, total y fechas.

Estados válidos:

- PENDIENTE
- CONFIRMADO
- PREPARANDO
- COMPLETADO
- CANCELADO

6.6 order_items
------------------------------------------------------------

Almacena suplemento relacionado, nombre histórico del producto, precio
unitario, cantidad y total de la línea. La instantánea permite conservar
el contenido histórico aunque después cambie el producto.

6.7 sessions
------------------------------------------------------------

Almacena hash SHA-256 del token de sesión, hash SHA-256 del token CSRF,
usuario, expiración y fecha de creación. Los tokens originales no se
guardan en la base de datos.

6.8 Datos iniciales
------------------------------------------------------------

El archivo de semillas es idempotente e incluye:

- 8 categorías.
- 8 objetivos.
- 11 ingredientes.
- 4 suplementos.
- Sus relaciones correspondientes.

10. AUTENTICACIÓN Y SEGURIDAD
============================================================

10.1 Contraseñas
------------------------------------------------------------

- Hash bcrypt.
- Costo predeterminado seguro de la biblioteca.
- Longitud admitida: 10 a 72 bytes.
- No se devuelven hashes al frontend.
- Cambiar la contraseña invalida sesiones existentes del usuario.

10.2 Sesiones
------------------------------------------------------------

- Tokens aleatorios criptográficos de 32 bytes.
- Solo se guardan hashes SHA-256.
- Duración predeterminada: 12 horas.
- Intervalo configurable: 1 a 168 horas.
- Las sesiones expiradas se purgan al crear nuevas sesiones.

10.3 Cookies
------------------------------------------------------------

Cookie de sesión:

- HttpOnly.
- SameSite=Lax.
- Path=/.
- Secure obligatorio en producción.

Cookie CSRF:

- Disponible para JavaScript.
- SameSite=Strict.
- Validada mediante encabezado en operaciones de escritura.

10.4 Protección CSRF
------------------------------------------------------------

Toda operación autenticada diferente de GET, HEAD u OPTIONS exige un
token CSRF correcto. La comparación utiliza hashes y tiempo constante.

10.5 Validación de solicitudes
------------------------------------------------------------

- Máximo de 1 MiB por cuerpo JSON.
- Rechazo de propiedades desconocidas.
- Rechazo de múltiples objetos JSON.
- Límites de longitud para texto.
- Validación de protocolos http y https para imágenes.
- Validación estricta de roles y estados.
- Precios e inventarios no negativos.
- Relaciones sin IDs repetidos.
- Pedidos de 1 a 50 líneas.
- Cantidades de 1 a 99.
- Claves idempotentes de 16 a 80 caracteres.

10.6 Limitación de solicitudes
------------------------------------------------------------

- Inicio de sesión: 10 intentos por minuto por IP/cuenta.
- Pedidos públicos: 5 por minuto por IP.

El límite vive en memoria. Se pierde al reiniciar el servidor y no se
comparte entre múltiples instancias.

10.7 Encabezados de seguridad
------------------------------------------------------------

- Content Security Policy.
- X-Content-Type-Options: nosniff.
- X-Frame-Options: DENY.
- Referrer Policy.
- Permissions Policy.
- Cross-Origin-Opener-Policy.
- Cache-Control: no-store en respuestas API sensibles.

10.8 Servidor HTTP
------------------------------------------------------------

- Lectura de encabezados: 5 segundos.
- Lectura total: 15 segundos.
- Escritura: 30 segundos.
- Conexión inactiva: 60 segundos.
- Encabezados máximos: 1 MiB.


11. FLUJO DE PEDIDOS
============================================================

1. El cliente crea una clave idempotente UUID.
2. El servidor obtiene un hash SHA-256.
3. Se genera el ID interno y número MAZ.
4. Se valida al cliente y cada producto.
5. TiDB bloquea inventario mediante SELECT ... FOR UPDATE.
6. Se comprueba que el producto esté activo y tenga existencia.
7. Se crea el pedido.
8. Se crean sus partidas.
9. Se descuenta el inventario.
10. Se confirma la transacción.
11. Se devuelve el pedido creado.

La idempotencia evita duplicar un pedido cuando el navegador reintenta
una solicitud.

Observación: el endpoint contiene múltiples sentencias SQL y control
explícito de transacción. TiDB soporta transacciones explícitas, pero el
flujo completo de compra no se ejecutó durante la auditoría para evitar
modificar existencias reales. Debe agregarse una prueba controlada en una
base separada.

Referencia:
https://docs.pingcap.com/tidbcloud/transaction-overview/


12. SISTEMA DE RESPALDOS
============================================================

El respaldo se solicita mediante:

POST /api/backups

Solo el administrador puede ejecutarlo.

El servidor consulta diez tablas de negocio:

- Usuarios.
- Categorías.
- Objetivos.
- Ingredientes.
- Suplementos.
- Relaciones de suplementos.
- Pedidos.
- Partidas de pedidos.

La tabla sessions se excluye intencionalmente.

Nombre del archivo:

maz-suplementos-AAAA-MM-DDTHHMMSSZ.sql

La respuesta incluye:

- Content-Disposition: attachment.
- Contenido SQL.
- Hash SHA-256 del archivo.

El navegador lo guarda en la carpeta de descargas configurada en la
computadora. Ya no se genera como JSON dentro de la carpeta del proyecto.

El respaldo contiene hashes bcrypt porque forman parte de la tabla de
usuarios, pero no incluye:

- Contraseñas en texto plano.
- Clave pública de Data Service.
- Clave privada de Data Service.
- Tokens activos de sesión.

Limitaciones:

- Las tablas se descargan mediante solicitudes independientes.
- No constituye un snapshot global transaccional.
- Puede haber diferencias si existen escrituras concurrentes.
- La restauración no se probó en una instancia TiDB separada durante
  esta auditoría.

16. HALLAZGOS Y RIESGOS PENDIENTES
============================================================

16.1 Prioridad alta antes de producción
------------------------------------------------------------

1. Rotar la contraseña de la cuenta TiDB y la clave Data API porque se
   compartieron durante la configuración, aunque no aparecen en Git.

2. Establecer expiración periódica para la clave Data API. Actualmente
   tiene acceso ReadAndWrite y no expira.

3. Desplegar exclusivamente mediante HTTPS y activar cookies Secure.

4. Mantener /users/bootstrap fuera de línea después de la inicialización.

16.2 Prioridad media
------------------------------------------------------------

1. Implementar CI en GitHub Actions con formato, compilación, pruebas,
   go vet, Gitleaks, análisis estático y Playwright.

2. Implementar una bitácora persistente de auditoría con usuario, acción,
   entidad, ID, fecha, resultado y origen.

3. Mover el rate limiting a Redis, base de datos o gateway al utilizar
   varias instancias.

4. Configurar proxies confiables antes de aceptar direcciones IP
   reenviadas.

5. Crear respaldos consistentes mediante snapshot o exportación nativa.

6. Probar restauraciones regularmente en una base aislada.

7. Ejecutar pruebas transaccionales de pedidos en un entorno no
   productivo.

8. Supervisar cambios de TiDB Data Service por su estado Preview.

16.3 Prioridad baja
------------------------------------------------------------

- Evitar registrar el nombre completo del usuario en accesos fallidos.
- Añadir métricas y alertas.
- Añadir identificadores de correlación por solicitud.
- Documentar objetivos de recuperación RPO y RTO.
- Añadir pruebas de accesibilidad automatizadas.
- Incorporar una política formal de retención de respaldos.

Maz-Suplementos presenta una arquitectura razonable y bien separada para
su alcance:

- El frontend no tiene acceso directo a la base de datos.
- Las credenciales permanecen en el backend.
- Los roles se validan del lado servidor.
- Las contraseñas están protegidas con bcrypt.
- Las sesiones usan tokens aleatorios y hashes.
- Las operaciones autenticadas están protegidas con CSRF.
- El acceso SQL está contenido en endpoints parametrizados.
- Los respaldos se entregan como archivos SQL descargables.
- La interfaz mantiene la sesión al regresar al inicio.
- La base, Data Service, backend y frontend están conectados y operativos.

El sistema puede considerarse funcionalmente completo para el alcance
definido y apto para entrega académica o uso interno controlado. No debe
declararse todavía como producción empresarial sin resolver la rotación
de secretos, CI, auditoría histórica, consistencia de respaldos, HTTPS y
operación distribuida.
